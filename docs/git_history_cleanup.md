# Removing the identity-resolution CSV from Git history

> **This has already been done.** It is written down because the procedure is
> worth keeping, because the verification steps are worth re-running, and
> because anyone finding this file should know the state rather than repeat the
> work. The record of what was done is at the bottom.

## What the file was

`docs/identity_resolution_footystats.csv` — 8,575 rows, one per player in the
provider's universe, each carrying a real person's name, date of birth and
nationality. It was generated by `pipelines.identity_resolution.resolve` into
`docs/`, which is tracked, and it was therefore committed to a public
repository and stayed there across three commits.

That the data derives from a provider does not make it less personal, and
`docs/` is not a place where files go unnoticed — it is the first place a
reader looks.

## Current state

- **Not in the working tree.** The resolver writes the row-level output to
  `data/processed/`, which is git-ignored.
- **Not in the index, and cannot return.** `.gitignore` refuses
  `docs/identity_resolution*.csv` while allowing
  `docs/identity_resolution_example.csv`.
- **Not in history.** Removed by `git filter-repo`; see the record below.
- **Replaced.** `docs/identity_resolution_example.csv` shows the columns using
  six invented players with synthetic ids.
- **Aggregates still published.** `docs/identity_resolution_footystats.md`
  carries matched, ambiguous and unmatched counts, naming nobody.
- **Guarded.** `backend/tests/test_personal_data_not_published.py` asserts all
  of the above, including that no tracked CSV carries identifying columns at
  scale.

## Verifying it, at any time

```bash
git log --all --oneline -- docs/identity_resolution_footystats.csv
```

Empty output means no commit touches the path. Stronger, because it searches
content rather than paths:

```bash
git rev-list --all | while read c; do git grep -l "<a name from the file>" "$c" -- 2>/dev/null; done
```

Empty output means the data is in no commit.

**Do not substitute a real name into this document.** Take the probe from the
regenerated output in `data/processed/`, which is git-ignored, run the search,
and leave the placeholder as it is. An earlier version of this file carried a
real player's name inside that command, which put one back into a tracked file
in `docs/` — the precise thing the rewrite was for — and made the check
useless besides, since it then always matched this document and could never
return empty. A verification that cannot fail is not a verification.

And that the ignore rules are the right shape:

```bash
git check-ignore -v docs/identity_resolution_footystats.csv   # must match
git check-ignore -v docs/identity_resolution_example.csv      # must NOT match
```

## The procedure, if it is ever needed again

### 1. Confirm the file is actually in history

```bash
git log --all --oneline -- <path>
```

### 2. Close public access first

A rewrite takes minutes and a force-push takes seconds, but the window between
deciding and finishing is a window in which the data is still public. Making
the repository private is instant and covers every old commit at once:

```bash
gh repo edit <owner>/<repo> --visibility private --accept-visibility-change-consequences
```

Check for forks before anything else. A fork holds its own copy of the objects
and a rewrite of the original does not touch it:

```bash
gh repo view <owner>/<repo> --json forkCount,visibility
```

### 3. Back up

```bash
git clone --mirror . ../<repo>-prerewrite-backup.git
```

A mirror clone holds every ref and every object. If the rewrite goes wrong,
this is the only way back.

### 4. Rewrite

`git filter-repo` is the right tool — `filter-branch` is deprecated, far
slower, and easy to get subtly wrong.

```bash
pip install git-filter-repo
python -m git_filter_repo --invert-paths --path <path> --force
```

It removes the `origin` remote deliberately, so a force-push cannot happen by
reflex. Re-add it when the result has been checked:

```bash
git remote add origin <url>
```

### 5. Verify before pushing

Run the verification commands above. Then confirm the working tree still holds
what it should, and that the test suite passes against the rewritten tree.

### 6. Force-push

```bash
git push --force origin main
```

### 7. Verify the remote

```bash
git clone <url> /tmp/verify && cd /tmp/verify
git log --all --oneline -- <path>    # must be empty
```

## Consequences, stated plainly

- **Every commit hash from the first occurrence onward changes.** In this
  repository that was 51 of 57 commits — the file was added early, so nearly
  the whole history was rewritten.
- **Every existing clone is now incompatible.** Anyone holding one must
  re-clone. A `git pull` produces a mess of divergent history, and a `git push`
  from an old clone would restore the removed objects.
- **Forks are not touched.** A fork keeps its own objects. This is why the fork
  count is checked before starting.
- **A rewrite is not erasure on a hosting platform.** GitHub keeps unreachable
  objects for a period and can serve them by SHA; cached views and the API may
  still hold them. Removing them entirely requires asking GitHub Support to
  purge the cache. **Treat the data as disclosed** and act on that basis rather
  than assuming a rewrite undoes the disclosure.
- **Open pull requests referencing rewritten commits break.**

## What was actually done here

| | |
| --- | --- |
| Repository made private | before the rewrite, closing public access immediately |
| Forks at that moment | 0 — so no copy survived outside the repository |
| Stars | 0 |
| Backup | `~/Desktop/scouting-prerewrite-backup.git` (mirror clone) |
| Tool | `git filter-repo 2.47.0`, `--invert-paths --path docs/identity_resolution_footystats.csv` |
| Commits rewritten | 51 of 57 |
| Verification | fresh clone of the remote: 0 commits touch the path; a content search for a name from the file returns nothing in any commit |
| Test suite after rewrite | passing |

The zero fork count is what makes the removal complete rather than nominal. A
single fork would have retained the objects beyond the owner's reach.

## The rule that keeps it from happening again

Generated output that names people does not go in a tracked directory.
`pipelines/identity_resolution/resolve.py` writes to `data/processed/`;
`.gitignore` refuses the old path and any sibling; and the test file named
above fails the build if a tracked CSV ever carries identifying columns at
scale. The aggregate report is the part meant to be published, and it stays.
